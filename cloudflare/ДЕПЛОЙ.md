# Arc на Cloudflare — как это устроено и что делать

## Как выпускаем обновления

Версия меняется **только при масштабных изменениях**; мелкие правки уходят на сайт без новой
версии. Полная история — в [`../CHANGELOG.md`](../CHANGELOG.md).

**Крупное обновление** (новый раздел, смена протокола или модели данных, заметный интерфейс):

1. поднять версию в `src/hub.js`, `public/index.html`, `mobile/package.json`,
   `desktop/package.json`, `versionCode`/`versionName` в `mobile/android/app/build.gradle`;
2. поднять кэш service worker в `public/sw.js` (`arc-shell-vN`);
3. `node scripts/build-mobile-www.mjs` → `npx cap copy android` → `gradlew assembleRelease`,
   новый APK в `public/download/Arc.apk`;
4. при изменениях оболочки — `npm run build` в `desktop/`, порезать exe на части,
   обновить `public/updates/parts/manifest.json` и `latest.yml`;
5. прогнать все наборы: `test-*.mjs`, клиент, мобильную сборку и оболочку;
6. `npm run deploy`, проверить живые наборы (`*-live.mjs`);
7. закоммитить, запушить и обновить GitHub-релиз с APK и установщиком;
8. перенести раздел «Не выпущено» из `CHANGELOG.md` в раздел новой версии.

**Мелкая правка** (тексты, подсказки, стили, баг на сайте):

1. прогнать только затронутые тесты;
2. поднять кэш service worker, чтобы клиент подхватил новую оболочку;
3. `npm run deploy`;
4. дописать пункт в «Не выпущено» в `CHANGELOG.md`.

APK в мелких правках не пересобирается: интерфейс вшит внутрь, поэтому всё важное для
телефона копится до крупного релиза. Исключение — поломка, без которой APK не работает.
Установщик Windows обычно тоже не трогаем: оболочка открывает живой сайт и получает правки
сразу; пересобираем, только когда меняется сам `main.js`/`preload.js`.

## Версия 1.6.0 — знакомство и статистика

**Экран знакомства.** Пока ни один чат не открыт, клиент показывает блок `#welcome` вместо
пустой ленты: заголовок, три преимущества (приватные каналы, звонки в личке, файлы и поиск),
кнопки «Открыть демо-канал», «Добавить друга», «Создать канал» и мини-превью демо-канала.
Личные сообщения при этом остаются в списке слева. Вход в любой чат скрывает экран, а последний
открытый канал запоминается в `localStorage.lastRoom` — после перезагрузки человек возвращается
в него, а не на экран знакомства.

**Демо-канал.** При регистрации `ensureDemoChannel(key)` создаёт личный канал (адрес `start`,
заголовок «Добро пожаловать», `channelMeta[room].demo = true`) и пять сообщений от автора `Arc`.
Сообщения помечены `external: 'demo'`, поэтому `purgeOrphans()` не считает их осиротевшими и не
удаляет при чистке. Канал принадлежит создателю: его можно удалить, переименовать и позвать
друзей, как любой другой; в панели канала подпись объясняет, что это экскурсия.

- `demo_open` — кнопка «Открыть демо-канал»: возвращает существующий демо-канал, а если его
  удалили — создаёт заново; повторные нажатия не плодят копии;
- новый человек не видит демо-канал другого: он входит в `channelItems` только своего владельца;
- в `channelView` появилось поле `demo`, клиент по нему показывает подпись в панели.

**Ссылка-приглашение.** У канала появился код, который работает как право войти:
`store.channelCodes[room] = { code, created, uses }` — 10 символов из `INVITE_CODE_CHARS`.
Код создаётся сразу при создании канала и при миграции старым каналам, поэтому ссылка есть
с первого дня. В `channelView` поля `invite` и `inviteUses` отдаются только создателю —
остальные участники кода не видят.

| Событие | Что делает |
| --- | --- |
| `channel_invite_reset { room }` | создатель получает новый код, старый сразу перестаёт работать |
| `channel_invite_off { room }` | ссылка отключается, пока не создадут новую |
| `channel_join { code }` | проверяет код, лимит участников и частоту попыток (10 в минуту), добавляет человека, присылает `channels`, `history` и `channel_created`; повторный вход не дублирует участника и не расходует код |

Ссылка выглядит как `https://<сервер>/?join=КОД`. Клиент запоминает код до входа в аккаунт
(на экране входа появляется подсказка), а после `hello` отправляет `channel_join` и убирает
параметр из адреса. В APK ссылка собирается от `window.__ARC_SERVER__`, поэтому её можно
отправить другу в любом мессенджере. Коды удаляются вместе с каналом и при чистке
осиротевших каналов; при добавлении участника по ссылке создатель сразу получает обновлённый
состав, а остальным участникам уходит уведомление.

**Счётчики.** Событие `stats_get` (только владелец) отвечает `stats`; данные считаются
обходом состояния в момент запроса, без внешней аналитики и без хранения агрегатов:

| Поле | Что внутри |
| --- | --- |
| `users` | всего, онлайн, новые за сутки и за неделю, забанено, замьючено |
| `messages` | всего и за последние сутки |
| `channels` | всего каналов, суммарно участий, из них демо |
| `dms` | личных комнат и сообщений в них за сутки |
| `media` | количество вложений, занято байт, лимит хранилища |
| `invites` | кодов всего, активных, суммарно использований |
| `moderation` | сотрудников, забанено |
| `backups` | дата последней копии, сколько храним |
| `signups` | новые регистрации по дням за 7 дней (для графика) |

История короткая (300 сообщений на комнату), поэтому подсчёт — один проход по состоянию.
В «Управлении» это карточки и столбики за неделю, кнопка «Обновить» и строка с кодами,
сотрудниками, банами и датой копии.

**Тесты.** `test-onboarding.mjs` (демо-канал: создание, экскурсия, приватность, повторное
открытие, удаление и восстановление) и `test-stats.mjs` (закрыто участнику, цифры сходятся,

## Версия 1.5.0 — приватные каналы

Общих каналов больше нет. Канал — это отдельная комната со своим создателем и списком
участников: пока создатель не позовёт человека, тот канал не видит и не получает из него
ни одного события. Основной способ общения — личные сообщения, каналы идут отдельно.

**Модель данных.** В состоянии появился `store.channelMeta`:

```js
channelMeta[room] = { owner: '<логин>', members: ['<логин>', ...], title: 'Друзья', created: 1700000000000 }
```

- `room` — прежний адрес комнаты (латиница, до 24 символов). Название на экране — `title`,
  поэтому канал может называться «Друзья», а адрес быть `ch-1a2b3c`;
- `store.channels` остался списком всех адресов, но клиенту он отдаётся **отфильтрованным**:
  `visibleChannels(key)` — только те каналы, где человек в `members`;
- старые каналы из прошлых версий при первом запуске получают владельца (владельца сервера)
  и всех существующих пользователей в участники, чтобы переписка не пропала.

**Права** (проверяются на сервере, а не только в интерфейсе):

| Действие | Кто может |
| --- | --- |
| видеть канал, читать историю, искать по нему | участник |
| писать, реагировать, редактировать своё, звонить в голос | участник |
| переименовать, позвать, убрать участника, удалить | создатель канала |
| удалить любое сообщение в канале | создатель канала, автор, модератор-участник |
| покинуть канал | участник (кроме создателя — он может только удалить) |

Лимиты: `CHANNEL_OWN_MAX` = 20 своих каналов на человека, `CHANNEL_MEMBERS_MAX` = 40
участников в канале, `CREATE_HOURLY` = 10 новых каналов в час. Название — до
`CHANNEL_TITLE_MAX` = 60 символов, эмодзи и кириллица допустимы.

**Что изменилось в протоколе.** Добавлены события клиент→сервер `channel_add`, `channel_kick`,
`channel_leave`, `channel_rename`; сервер→клиент — `channel_added`, `channel_removed`, а `channels`
теперь приходит каждому свой (`channels` — адреса, `items` — название, создатель, участники,
онлайн). Всё, что происходит в канале (`msg`, `msg_edit`, `msg_delete`, `msg_reaction`, `typing`,
`voice_state`), уходит только участникам через `sendChannel`; `hello` тоже отдаёт только свои
каналы и `channelItems`. Поиск, `join`, голос и вложения проверяют участие.

**Вложения стали приватными.** При отправке сообщения файл привязывается к комнате
(`media.room`), а `GET /media/<id>` требует токен: `?t=<токен>` или заголовок `x-token`.
Автор видит только что загруженный файл, участники — файлы своего канала или лички,
остальные получают `403`. Заголовок кэша стал `private, max-age=86400`. Старые вложения
при первом запуске получают `media.room` из истории (миграция `mediaCheck`), иначе они
были б недоступны участникам.

**Мост Matrix.** Сам каналы не создаёт: если в настройках указан удалённый канал, мост
пишет «Канал для моста не найден» и не делает вид, что всё работает. Общих каналов, куда
по умолчанию пишет мост, больше нет.

**Клиент.** Личные сообщения в списке идут первыми, ниже — «Каналы» с замком 🔒 и числом
участников. В шапке канала — кнопка 👥 с панелью: участники (кто в сети), кнопки-чипы
друзей для приглашения, поле «позвать по имени», переименование, «Покинуть канал» и
«Удалить канал». В пустом состоянии — подсказка создать канал; личные чаты работают всегда.

## Звонки в личку

Голос раньше работал только в каналах: `voice_join` проверял
`this.store.channels.includes(room)`. Теперь пускает и в личку, но только её участников —
`voiceJoinAllowed(key, room)`: канал либо `dm:<a>|<b>`, где `key` один из двоих.

Звонок — это приглашение, а не мгновенный вход в голос:

| Клиент → сервер | Что делает сервер |
| --- | --- |
| `call_start { room }` | проверяет, что это личка и звонивший её участник; если собеседник уже в голосе — отвечает `call_busy`; иначе шлёт ему `call_incoming` и звонившему `call_ringing` |
| `call_accept { room }` | принимает только тот, кому звонят; звонившему уходит `call_accepted`, принявшему — `call_answered` |
| `call_decline { room }` | звонившему уходит `call_declined` |
| `call_cancel { room }` | получателю уходит `call_cancelled` (звонивший передумал или не дождался) |

Приглашение живёт `CALL_RING_MS` = 60 секунд. Если приложение у получателя было закрыто,
при подключении сокета сервер заново присылает `call_incoming`, так что звонок не теряется.
При отключении сокета `dropCallsOf(name)` снимает висящие приглашения и говорит второй стороне.

Приватность: `broadcastVoice(room)` рассылает `voice_state` только участникам приватного
канала и только двоим участникам лички, а не всем — иначе по рассылке было бы видно,
кто с кем говорит.

Сама передача звука — существующий WebRTC: `rtc` пересылает offer/answer/ICE только тем, кто
стоит в одной голосовой комнате, поэтому в личке схема не менялась.

## Вложения: картинки и файлы

Вложения лежат в хранилище Durable Object кусками по 96 КБ (`media:<id>:<i>`),
метаданные — в `store.media`.

- **картинки** (PNG, JPG, WEBP, GIF): до 2,5 МБ, проверяются по сигнатуре файла,
  сжимаются на клиенте до 1600px, отдаются как превью;
- **файлы любых типов**: до 10 МБ, имя приходит в заголовке `x-filename`
  (в процентном кодировании) и чистится от пути, кавычек и `..`;
- отдаются по `/media/<id>`: картинки — inline, файлы — с `content-disposition:
  attachment` и исходным именем (`filename*` для кириллицы);
- общий бюджет хранилища — 300 МБ и не больше 120 вложений; старое вытесняется
  по времени загрузки (`trimMedia`), чтобы десять файлов по 10 МБ не съели объект;
- в CORS разрешены заголовки `x-token` и `x-filename`, иначе preflight отсекает
  отправку файла из мобильного приложения.

## Резервные копии и восстановление

Вся база лежит одним JSON в Durable Object, поэтому снимки делаются там же:

- каждый день объект просыпается по таймеру (`alarm`) и кладёт снимок в хранилище
  под ключ `bkp:<дата>`; хранятся последние **7** (`BACKUP_KEEP`);
- таймер взводится автоматически при первом обращении к объекту, отдельный
  Cron Trigger не нужен; если включён мост Matrix, тот же таймер обслуживает и его;
- в снимок не попадают токены, счётчики перебора и лимиты — после восстановления
  сессии остаются текущими, а не «воскресают» старые;
- **скачивание**: `GET /api/backup?date=ГГГГ-ММ-ДД` с заголовком `x-token` владельца.
  По умолчанию хэши паролей вырезаны; для полного переноса на другой сервер —
  `&full=1`;
- **восстановление**: в настройках, раздел «Управление» → «Восстановить». Перед
  откатом текущее состояние сохраняется как `before-restore-<дата>`, поэтому
  отменить восстановление можно тем же способом;
- протокол: `backup_list`, `backup_now`, `backup_restore { date }` →
  `backup_state { items, lastBackup, keep }`.

### Сброс пароля

Почты у аккаунтов нет, поэтому пароль возвращает владелец: `password_reset { name }`
генерирует временный пароль из 8 символов, перезаписывает хэш (PBKDF2), гасит все
сессии участника и один раз показывает пароль владельцу (`password_reset_done`).
Передать его нужно лично — в базе он не хранится.

## Проверки (CI)

`.github/workflows/ci.yml` на каждый push в `main` и на pull request:

1. `npm run check` — синтаксис сервера;
2. `npm test` — клиентские наборы в jsdom;
3. `npm run test:mobile` — сборка мобильного интерфейса и её проверка;
4. `npm run deploy:dry` — пробная сборка воркера;
5. отдельная задача поднимает `wrangler dev` с чистой базой и прогоняет
   `test-server`, `test-scenario-a`, `test-moderation`, `test-backup`, `test-e2e`.

Тесты ищут пути относительно себя (`test-helpers.mjs`), поэтому запускаются
и локально, и в CI без правок.

## Роли и модерация

Три роли: **владелец** (`owner`), **сотрудник** (`staff`) и участник.

| Действие | Участник | Сотрудник | Владелец |
| --- | --- | --- | --- |
| Удалить своё сообщение | да | да | да |
| Удалить чужое сообщение | нет | да | да |
